## The ratio against the workload mix

Produced by `harness/workload_sweep.py` on `table_640x480` (640x480), 500 measured frames per implementation per configuration after 100 warm-up frames, against the 2000 of the headline run. Every configuration passed the equivalence gate before its row was written; the worst deviation column is what the gate observed.

The first row is the published configuration measured again at 500 frames, which is also the check on the shorter runs every other row uses. The 2000-frame run in the table above gives 58.031 ms and 86.905 ms at p50, a ratio of 1.50x; this sweep gives 53.160 ms and 84.613 ms, a ratio of 1.59x. The Python numbers agree to 3% and the C++ numbers do not, by 8%, on the same binary over the same corpus. Two runs of the same thing on this shared unpinned box differ by about that much: the repeat under threat T2 moves the same C++ figure by a comparable amount between its two runs, with the direction of the move not even consistent. So **compare rows within this table, not across to the headline**: every row here was taken by one script inside one window, and the curve is the comparison between them.

The headline 1.50x is one point on a curve, and this is the curve. Two constants set how much of the frame is bulk array work: `deproject.stride`, which divides the point count by its square, and `plane.iterations`, which divides the candidate count. Shrinking either shrinks the RANSAC plane stage, which is where Python spends the frame inside compiled loops rather than in the interpreter, and leaves untouched the small-matrix stages where it pays per call and not per element. Nothing else about the pipeline changes: both implementations read the same derived config file, and the deviate table each configuration uses is a prefix of the committed one, so a 32-iteration run scores the first 32 triples the 128-iteration run scored.

The remainder run the whole pipeline, so the row is still comparable, with that fraction of cheaper samples in it.
* **stride 8, 128 iters**: plane is 91.9% of the C++ frame and 70.3% of the Python one; the grasp, IK and trajectory stages together are 0.3% of the Python frame against 0.0% of the C++ one. Ratio 2.12x at p50, 2.06x at p99. 450 of 500 measured samples bail out early (450 found no cluster holding `cluster.min_points` at S4), so they never reach grasp synthesis, IK or the trajectory. At 90% this row is mostly timing a shorter pipeline than the others, and it is the answer to whether a stride like this is free: subsampling that hard takes the object out of the cloud along with the cost.
* **stride 1, 32 iters**: plane is 85.8% of the C++ frame and 61.7% of the Python one; the grasp, IK and trajectory stages together are 2.7% of the Python frame against 0.2% of the C++ one. Ratio 4.20x at p50, 3.93x at p99.
* **stride 1, 8 iters**: plane is 68.9% of the C++ frame and 56.6% of the Python one; the grasp, IK and trajectory stages together are 3.2% of the Python frame against 0.5% of the C++ one. Ratio 7.89x at p50, 5.95x at p99.

**The `py block` column is a knob that had to move.** `implementation.ransac_block_points` is read only by the Python plane stage, it changes memory traffic and never output, and its committed value of 512 was chosen when the distance block was 512 x 128 float64. Shrink the candidate count and that block stops filling the cache while the Python loop still runs once per 512 points, so the constant becomes a tax on a configuration it was not chosen for. Each row here re-chooses it by measurement over 40 frames per candidate, exactly the way the committed value was chosen, and the full curve is in `workload_sweep.json`. The candidates stop at 32,767 points because above that the Python stage's own partial sum overflows and the answer changes, which the gate caught the first time this sweep reached for a larger block: threat T1 in [../docs/METHOD.md](../docs/METHOD.md) has the detail. What holding the block fixed would have cost:

* stride 1, 32 iters: the Python plane stage runs at p50 40.659 ms with the committed 512-point block and 37.907 ms with the 2,048-point block this row uses. Reporting the first would have charged Python for a stale constant and called it a language cost.
* stride 1, 8 iters: the Python plane stage runs at p50 34.478 ms with the committed 512-point block and 30.986 ms with the 2,048-point block this row uses. Reporting the first would have charged Python for a stale constant and called it a language cost.

**Read the p50 column, not the p99 one.** Every configuration was measured 2 times end to end, and the table publishes the first repeat rather than the flattering one. Across repeats the p50 ratio moved by at most 0.39, which is 9% of the row it happened on, while the p99 ratio moved by up to 2.99, which is 63% of its row. The shape of the curve is a property of the pipeline; the p99 column on this box is a property of what else the box was doing, which is threat T2 arriving exactly where it was predicted to. Per-repeat ratios and the load average before every run are in `workload_sweep.json`.

The p99 columns come from 500 samples over 100 distinct store frames, so the value quoted is the 6th slowest sample of the run and carries the repeat structure described in threat T8. The p50 columns are the ones to lean on; the p99 columns are here because a ratio that moves at the median and not in the tail would be a different finding from one that moves in both.

The box is shared and unpinned, so the load average is recorded at both ends of the sweep: 0.50, 1.84, 1.98 at the start and 3.72, 2.93, 2.43 at the end. Threat T2 is why that matters and what it does not excuse.
