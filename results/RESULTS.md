## The ratio against the workload mix

Produced by `harness/workload_sweep.py` on `table_640x480` (640x480), 500 measured frames per implementation per configuration after 100 warm-up frames, against the 2000 of the headline run. Every configuration passed the equivalence gate before its row was written; the worst deviation column is what the gate observed.

The first row is the published configuration re-run at 500 frames, so it is also a check on the shorter runs the other rows use: the 2000-frame run in the table above gives 58.031 ms and 86.905 ms at p50 for 1.50x, and this sweep gives 53.344 ms and 90.350 ms for 1.69x.

The headline 1.50x is one point on a curve, and this is the curve. Two constants set how much of the frame is bulk array work: `deproject.stride`, which divides the point count by its square, and `plane.iterations`, which divides the candidate count. Shrinking either shrinks the RANSAC plane stage, which is the stage where NumPy and Eigen reach comparable compiled loops, and leaves the small-matrix stages where Python pays per call. Nothing else about the pipeline changes: both implementations read the same derived config file, and the deviate table each configuration uses is a prefix of the committed one, so a 32-iteration run scores the first 32 triples the 128-iteration run scored.

This row is not the same pipeline as the others: 0 of 500 measured frames found no plane and 450 found no cluster holding `cluster.min_points`, so they stop at S4 and never reach grasp synthesis, IK or the trajectory. * **stride 1, 32 iters**: plane is 86.0% of the C++ frame and 61.9% of the Python one; the grasp, IK and trajectory stages together are 2.7% of the Python frame against 0.2% of the C++ one. Ratio 3.90x at p50, 2.82x at p99.
* **stride 1, 8 iters**: plane is 68.8% of the C++ frame and 56.7% of the Python one; the grasp, IK and trajectory stages together are 3.1% of the Python frame against 0.5% of the C++ one. Ratio 8.22x at p50, 32.81x at p99.

**The `py block` column is a knob that had to move.** `implementation.ransac_block_points` is read only by the Python plane stage, it changes memory traffic and never output, and its committed value of 512 was chosen when the distance block was 512 x 128 float64. Shrink the candidate count and that block stops filling the cache while the Python loop still runs once per 512 points, so the constant becomes a tax on a configuration it was not chosen for. Each row here re-chooses it by measurement over 40 frames per candidate, exactly the way the committed value was chosen, and the full curve is in `workload_sweep.json`. What holding it fixed would have cost:

* stride 1, 32 iters: the Python plane stage runs at p50 41.308 ms with the committed 512-point block and 38.359 ms with the 2,048-point block this row uses. Reporting the first would have charged Python for a stale constant and called it a language cost.
* stride 1, 8 iters: the Python plane stage runs at p50 36.103 ms with the committed 512-point block and 31.800 ms with the 32,767-point block this row uses. Reporting the first would have charged Python for a stale constant and called it a language cost.

The p99 columns come from 500 samples over 100 distinct store frames, so the value quoted is the 6th slowest sample of the run and carries the repeat structure described in threat T8. The p50 columns are the ones to lean on; the p99 columns are here because a ratio that moves at the median and not in the tail would be a different finding from one that moves in both.

The box is shared and unpinned, so the load average is recorded at both ends of the sweep: 0.22, 1.22, 1.66 at the start and 3.73, 2.55, 2.10 at the end. Threat T2 is why that matters and what it does not excuse.
